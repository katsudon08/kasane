# なぜ KASANE を作るのか

本サービスの目的と、設計の拠り所にしている考え方を記します。
仕組みそのものは [spec/](spec/) を参照してください。

## プログラミング教育の領域で起きていること

小学校向けのプログラミング教材は、Scratch、ロボット、タンジブル教材、ゲーム型教材など、すでに多様なものが存在している。さらに、二人でロボットを操作する活動や、複数のエージェントを協働させる研究も存在しており、「教材がないこと」自体は現在の主要な課題ではない。

参照：[文部科学省「小学校を中心としたプログラミング教育ポータル ― 教材情報一覧」](https://www.mext.go.jp/miraino_manabi/teaching.html)

参照：[CoProStory: A Tangible Programming Tool for Children's Collaboration](https://repository.isls.org/handle/1/4408?mode=full)

一方、小学校プログラミング教育では、単にプログラムを書けるようになることではなく、目的を達成するために必要な動きを分解・手順化し、実行結果を踏まえて改善していく**プログラミング的思考**の育成が重視されている。

参照：[文部科学省「小学校プログラミング教育の手引（第三版）」](https://www.mext.go.jp/content/20200218-mxt_jogai02-100003171_002.pdf)

また、学校教育全体では、児童一人一人の学びと他者との学びを行き来させる **「個別最適な学び」と「協働的な学び」の一体的な充実** が求められている。

参照：[文部科学省「個別最適な学びと協働的な学びの一体的な充実」](https://www.mext.go.jp/a_menu/shotou/new-cs/senseiouen/mext_01317.html)

したがって現在求められているのは、新しいプログラミング教材を増やすことではなく、**一人一人が自分で考え、他者と考えを比較・更新し、実行結果を根拠として問題を改善していく学習を成立させること**である。

## 本質的な課題

本質的な課題は、**望ましい学習過程の成立が、教師の授業設計・声掛けや児童自身の行動に依存しやすいこと**にある。

例えば、二人で活動していても、一方だけが考えてもう一方が従っていれば、各児童の学びは保証されない。また、ロボットが失敗するたびに理由を考えず命令を変更しても課題をクリアできるのであれば、予測・原因分析・改善を伴う問題解決にはならない。

教師にとっても、多数の児童が同時に活動する中で、どのペアがどこでつまずき、誰が自分で考え、どのような理由でプログラムを変更しているのかを常に把握しながら、一人一人に適切な支援を行うことは難しい。

つまり解決すべきなのは教材不足ではなく、**「個人で考える → 他者と考える → 結果から原因を考える → 改善する」という学習過程を成立させるために、児童や教師が意識的に行動し続けなければならない状態**である。

この課題設定は、「教材そのものではなく、学習過程を構造化する」という方針を基にしている。

## 導入先の現状

導入先の小学校では、Scratch などのプログラミング教材は使われておらず、調べ学習や紙を使ったアンプラグドの学習が行われている。教師は ICT に不慣れで、パソコンを使うなら紙のほうがよいと考える水準にある。KASANE は、この状態の教師が使いたいと思えるものでなければならない。

## 理想状態

KASANE が目指すのは、**教材そのものが学習過程を構造化し、児童が普通に活動を進めることで、プログラミング的思考による問題解決と協働的な学びが自然に発生する状態**である。

児童は、まず一人で問題を捉えて自分の考えを持つ。その考えを実行前の予測として表現し、他者の異なる考えと比較・説明した上で共同で実行する。そして、予測と実際の差異から原因を考え、他者の考えを取り入れながら修正・再検証し、最後に協働によって得られたものを自分自身の理解へ戻す。

すなわち、KASANE では、**個人 → 協働 → 個人**と、**予測 → 実行 → 差異 → 原因 → 修正 → 再検証**という二つの循環を一つの学習体験として成立させる。

参照：[文部科学省「個別最適な学びと協働的な学び」](https://www.mext.go.jp/a_menu/shotou/new-cs/senseiouen/mext_01493.html)

教師は、この学習過程そのものを毎回の説明や声掛けによって成立させるのではなく、システムに基本的な進行を任せる。そして、各ペアの学習状況から支援が必要な児童を把握し、その児童の思考を深めるための個別支援に集中できる状態を目指す。

つまり KASANE の理想は、**「個別最適な学び」「協働的な学び」「プログラミング的思考による問題解決」を教師や児童の自発的な行動だけに委ねず、学習環境の構造として成立させること**である。

## 設計の原則

理想状態を学習環境の構造として成立させるために、KASANE は次の原則で設計する。原則を実装した仕組みは [児童フロー](spec/student-flow.md) と [教師フロー](spec/teacher-flow.md) を参照。

- **協働の前に、各児童が自分の考えを持つ。** 一方の児童だけが考え、もう一方が従う状態を防ぐため、相手と話す前に一人で考える段階を置く。
- **予測を実行の前提にする。** 「相手はどう動くか」「二台を一緒に動かすと何が起こるか」を双方が予測するまで実行できない構造とし、相手の考えを理解する必要性をシステム側から生み出す。PRIMM の Predict → Run → Investigate → Modify → Make と整合する。

  参照：[Sentance「PRIMM: A structured approach to teaching programming」](https://suesentance.net/2017/09/01/primm-a-structured-approach-to-teaching-programming/)

- **予測の誤りは自分の結果に返る。** 自分のプログラムが正しくても、相手の予測を誤れば相手の実際の動きに干渉されてゴールできない。予測が他人事にならない構造にする。
- **差異は見せるが、原因は教えない。** 実行後、システムは予測と実際の動きの差異を示すにとどめ、原因や答えは示さない。児童が差異を根拠に原因を考え、根拠を持って修正することを促す。

  参照：[Wong et al.「Engaging children in developing algorithmic thinking and debugging skills in primary schools」](https://link.springer.com/article/10.1007/s10639-024-12448-x)

- **プログラムは開示せず、言葉で伝える。** 相手の考えは口頭の説明でしか得られない構造にし、言語化と比較を必然にする。
- **教師は進行ではなく支援に集中する。** 学習過程の進行はシステムが担い、教師には各ペアの進行状況を示す。教師は全員に一律に介入するのではなく、支援が必要な児童に重点的に関わる。
- **手で入力しない。** 児童も教師も、識別も操作も QR コードをかざすだけで済むようにする。ICT に不慣れな教師が紙の教材と同じ感覚で使えることを優先する。
- **実証済みの進め方を残す。** ProgPath と同じ一台のロボットで解く進め方をシングルモードとして残し、その上にペアモードを置く。学校が実証を重ねてきた進め方を失わないためである。
