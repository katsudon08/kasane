## 前提となる負荷特性

技術選定の前に、このシステムがどういう負荷を受けるのかを確定させておきます。
ここを見誤ると、必要のない複雑さを最初から抱え込むことになります。

| 項目 | 見積もり |
| --- | --- |
| 1クラスの接続数 | 児童40 ＋ 教師1 ＝ **41** |
| 100校が同時に授業を行った場合 | 約 **4,100接続** |
| 1接続あたりのメッセージ頻度 | **1ラウンドに数回**（秒間ではない） |

つまり本サービスは「**接続数は多いが、スループットは極端に低い**」という特性を持ちます。

チャットやリアルタイムゲームのように毎秒大量のメッセージが飛ぶ構造ではありません。
[アーキテクチャ](アーキテクチャ.md)の「前提3」に書いた通り、実態は**バリア同期**であり、通信はフェーズの節目にしか発生しません。

## 言語：TypeScript で統一する

フロントエンドとバックエンドの両方を TypeScript で書き、**モノレポで型を共有します**。

```
kasane/
├─ apps/
│  ├─ web/       React + Vite
│  └─ server/    Node.js
└─ packages/
   └─ shared/    メッセージスキーマ / 軌跡 / プログラム表現 / 迷路 の型
```

### 理由

共有したいのは以下の二つです。

1. **WebSocket で飛ぶメッセージのスキーマ**
2. **軌跡（フレーム列）のデータ形式**

特に 2 は、4台のロボットの位置・向き・状態と、穴埋めによる地形変化を含む構造を毎フレーム送ります。
この形式がフロントとバックで食い違うと、**コンパイルは通るのに実行時に壊れる**という最も追跡しづらいバグになります。

型を一箇所に書いて両側から参照できることの価値は、このシステムでは特に大きくなります。

### 補足：シミュレーションロジックは共有しない

[アーキテクチャ](アーキテクチャ.md)の通り、シミュレーションは**サーバーにのみ**置きます。クライアントは軌跡を再生するだけです。
したがって「ロジックを共有するために TypeScript で統一する」のではありません。共有するのは**型だけ**です。

## フロントエンド：React（Vite）

クライアントはブラウザで動く Web アプリケーションとします。

### ブラウザを選んだ理由

QRカードを読むためカメラが必須ですが、選択肢はブラウザかネイティブアプリの二つでした。

| | ブラウザ | ネイティブアプリ |
| --- | --- | --- |
| 配布 | **URL を開くだけ** | MDM による配布が必要 |
| カメラ | `getUserMedia` で利用可能 | より高機能 |
| 制約 | **HTTPS が必須** | なし |

学校の GIGA 端末はアプリの配布に管理者の手続きが必要になるため、**URL を開くだけで使える**ことの価値が大きいと判断しました。

### クライアントの責務

React が担当するのは以下の三つだけです。

- QRコードの読み取り（カメラ）
- プログラム編集 UI
- 軌跡の再生描画（4台の重ね合わせ、ゴースト世界は半透明）

**シミュレーションロジックは持ちません。** サーバーから届いたフレーム列を再生するだけです。

### QRコードの読み取り

`BarcodeDetector` API はブラウザによって対応状況が異なり、iOS Safari では利用できません。
ライブラリ（jsQR / zxing-js / html5-qrcode など）を使う前提とします。

---

## バックエンド：Node.js

TypeScript で統一するため Node.js を採用します。

### 常駐プロセスが必要である点に注意

WebSocket は「繋ぎっぱなしの接続」を維持するため、**常駐するプロセスが必要**です。

Vercel Functions や Netlify Functions のような、リクエストのたびに起動して終了するサーバーレス環境には**載りません**。
フロントエンドをそうした環境に置くのは自由ですが、**バックエンドは常駐できる場所**に別途配置する必要があります。

## リアルタイム通信：WebSocket（Socket.IO）

### なぜ WebSocket なのか

「リアルタイムだから」ではありません。前述の通り、本サービスに高頻度の状態同期は存在しません。

WebSocket を選ぶ理由は次の二つです。

1. **サーバープッシュが必要** — 「相手が確定するのを待つ」ため、クライアントからの問い合わせでは成立しない
2. **接続の生死を検知できる** ← **こちらが本命**

2 が決定的です。バリア同期は「双方が揃うまで待つ」ため、**片方が離脱した瞬間にペアが永久に固まります**。
学校の Wi-Fi 環境では必ず起きる事故であり、これを検知できることが最も重要です。

サーバープッシュだけが目的なら SSE と HTTP POST の組み合わせでも足りますが、離脱の検知を含めると WebSocket が素直です。

### なぜ Socket.IO なのか

| 機能 | Socket.IO | 生の `ws` |
| --- | --- | --- |
| 自動再接続 | 組み込み | 自前で実装 |
| room 機能 | 組み込み | 自前で実装 |
| Redis adapter | 公式提供 | 自前で実装 |
| 依存の軽さ | 重い、独自プロトコル | 軽い |

[アーキテクチャ](アーキテクチャ.md)で定めた `notifyPair(pairId, message)` という送信経路は、Socket.IO の room 機能そのものです。
MVP を早く立ち上げる目的に対して有利と判断しました。

### 懸念とその評価

Socket.IO については以下の指摘があり、検討しました。

**指摘1：接続確立時に HTTP ロングポーリングを経由するため負荷が高い**

事実です。ただし二点の補足があります。

- クライアント側の設定 `transports: ['websocket']` の一行で無効化できる
- 負荷がかかるのは**接続確立のときだけ**で、アップグレード後は通常の WebSocket として動作する

そして、このフォールバック機構は本サービスにおいては**保険としての価値があります**。
学校のフィルタリング機器が WebSocket のアップグレードを阻む可能性があるためです。
「無駄な負荷」として切り捨てようとしているものが、導入先の環境では生命線になりえます。

**実環境で検証してから絞るべき**であり、事前に決め打つべきではないと判断しました。

**指摘2：多数の学校から同時接続されるとスケールしない**

前述の負荷特性に照らすと、当たりません。
数千の**低トラフィック**接続であれば Node.js の1プロセスで捌けます。

スケーラビリティを理由に別ライブラリを推奨する記事の多くは、**毎秒大量のメッセージが飛ぶ前提**で書かれています。
自分のシステムの負荷特性に当てはまるかを確認せずに一般論を適用すると、必要のない複雑さを最初から抱え込むことになります。

### この判断は後から変えられる

そもそもこの選定は、**今決め打つ必要がありません**。

- **状態の権威を DB に置いた**ことで、接続層は「ただの配達経路」に降格している
- **送信を `notifyPair()` の一関数に閉じ込めた**ことで、ライブラリ固有の呼び出しはその関数の中にしか現れない

この二つにより、接続ライブラリの差し替えは現実的なコストに収まります。

> **可逆性は、変更が及ぶ面を一箇所に絞ることで作られる。**

予測で複雑さを先払いせず、実際に困ったときに判断します。

## データベース：PostgreSQL

[アーキテクチャ](アーキテクチャ.md)の通り、進行状態と履歴の両方を DB に置きます。

PostgreSQL を選ぶ理由は以下の通りです。

- フェーズ遷移で使う**条件付き UPDATE と `RETURNING`** がそのまま書ける
- プログラムの生の列やシミュレーション結果を **JSONB** に格納できる
- 書き込み頻度が1ラウンドに数回しかないため、性能上の制約が実質存在しない

---

## DB アクセス：Drizzle または Kysely

**Prisma は採用しません。**

理由は、フェーズ遷移の実装にあります。すべての遷移で以下のような SQL を書きます。

```sql
UPDATE pairs SET phase = 'implementation'
 WHERE id = $1 AND phase = 'prediction';
```

「遷移前の状態を WHERE 条件に含める」という原則は、二重遷移を構造的に防ぐための中核です（詳細は [アーキテクチャ](アーキテクチャ.md)）。

Prisma のような SQL を隠すタイプの ORM は、こうした条件付き UPDATE や `RETURNING` を素直に表現できず、結局 `$queryRaw` に逃げることになります。
本サービスではこの書き方を**全フェーズ遷移で使う**ため、**SQL に近い層**である Drizzle や Kysely の方が適しています。

## デプロイ

| 対象 | 置き場所 |
| --- | --- |
| フロントエンド | 静的ホスティングで可 |
| **バックエンド** | **常駐プロセスを置けるクラウド**（Fly.io / Render / Railway / Cloud Run / ECS など） |
| データベース | マネージドな PostgreSQL |

### HTTPS は必須

ブラウザでカメラを使うには、セキュアコンテキスト（HTTPS、または `localhost`）である必要があります。

このため、**教室内 LAN にサーバーを立てる構成は採用しませんでした**。
自己署名証明書を各端末に信頼させる必要があり、児童・教師に管理者権限のない GIGA 端末では現実的でないためです。

### MVP は 1 インスタンス

複数インスタンスに増やすと、状態の正しさは DB が守るものの、**通知の到達性が壊れます**（詳細は [アーキテクチャ](アーキテクチャ.md)）。
MVP では 1 インスタンスで運用し、そのことを自覚した上で `notifyPair()` による備えだけを置いておきます。

## テスト

技術選定と同じくらい重要な点として、以下は**自動テストでしか守れません**。

| 対象 | 理由 |
| --- | --- |
| **フェーズ遷移の競合** | 二人が同時に確定を押したときの不具合は、数ミリ秒のタイミング差で発生の有無が変わり、**手動では再現しない** |
| **情報の非対称性** | 児童Aに送られるペイロードに相手の命令列が含まれていないことを、テストで固定しておく必要がある |

シミュレーションエンジンは純粋関数として実装するため、ユニットテストで十分に検証できます。
迷路とプログラムが決まれば結果は決定論的であり、ここが品質の要になります。
