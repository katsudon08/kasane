## 全体構成

```
┌─ ブラウザ ────────────────┐          ┌─ サーバー（1プロセス）────────────┐
│                            │          │                                    │
│  QRコードの読み取り        │          │  transport/  接続とメッセージ      │
│  プログラム編集 UI         │◄──WS───► │  domain/     フェーズ / プログラム │
│  軌跡の再生描画            │          │              / シミュレーション    │
│                            │          │  view/       配信内容の制御        │
│  シミュレーションは持たない│          │  db/         データアクセス        │
└────────────────────────────┘          └─────────────────┬──────────────────┘
                                                          │
                                                    データベース
```

ブラウザは**入力と描画だけ**を担当し、計算はすべてサーバーが行います。
サーバーは**1プロセス**で、児童と教師の両方の接続を行います。

---

## ブラウザ

### 責務

ブラウザが担当するのは以下の三つです。**ロジックは持ちません。**

| 責務 | 内容 |
| --- | --- |
| QRコードの読み取り | カメラでカードを読み、コマンド列を組み立てる |
| プログラム編集 | 読み取ったコマンド列の表示・修正、くりかえしの回数入力 |
| 軌跡の再生描画 | サーバーから受け取ったフレーム列を再生する |

### 軌跡の再生

サーバーから受け取るのは**フレーム列**であり、プログラムではありません。
ブラウザはフレームを順に描画するだけで、次の位置を自分で計算することはありません。

実行フェーズでは 2 本のフレーム列（実体世界とゴースト世界）を重ねて描画します。
ゴースト世界のロボットは半透明で描画します。

## サーバー

### レイヤ構成

| レイヤ | 責務 |
| --- | --- |
| `transport/` | 接続の受け付け、メッセージの受信と送信 |
| `domain/` | フェーズ状態機械、プログラムのパースと展開、シミュレーション |
| `view/` | 誰に何を送ってよいかの判断 |
| `db/` | データアクセス |

**`transport/` のハンドラが直接 `socket.emit` を呼ぶことを禁じ、送信内容の組み立てはすべて `view/` を通します。**

### WebSocket

#### エンドポイント

接続時にロールを決定します。プロセスは分けず、エンドポイントとハンドラだけを分離します。

| エンドポイント | 接続元 |
| --- | --- |
| `/ws/student` | 児童 |
| `/ws/teacher` | 教師 |

#### メッセージ

| 向き | メッセージ |
| --- | --- |
| 児童 → サーバー | `join` / `resume` / `simulate` / `confirm.prediction` / `confirm.implementation` / `advance` |
| サーバー → 児童 | `state` / `simulation.result` / `phase.changed` / `execution.result` / `review.data` / `partner.disconnected` |
| 教師 → サーバー | `session.create` / `pair.assign` / `student.reissueToken` |
| サーバー → 教師 | `session.state` |

#### 参加と再接続

| 手順 | 実行者 |
| --- | --- |
| セッション（授業）の作成、ルームコードの発行 | 教師 |
| ペアの編成 | 教師 |
| 初回参加（ルームコード＋出席番号で名乗る） | 児童 |
| トークンの発行 | サーバー |

- **初回参加時** — 児童が名乗る。サーバーがトークンを発行し、端末に保持させる
- **再接続時** — 名乗らせず、**トークンで照合する**

一度使われた出席番号は埋まり、二重参加を弾きます。
教師が担当するのは「トークンごと失った児童の救済」という例外経路のみです。

#### 離脱の検知

接続の切断を検知し、相手の児童に `partner.disconnected` を送ります。

#### 通知の送信

ペアへの送信は **`notifyPair(pairId, message)` の一関数に集約します。**
`transport/` 以外から送信処理を呼び出しません。

MVP は 1 インスタンスで運用します。

### データベース

#### 状態の配置

| 種類 | 置き場所 |
| --- | --- |
| フェーズ、確定フラグ、提出プログラム、履歴 | **データベース**（source of truth） |
| 接続中の児童、送信先のソケット | メモリ（揮発） |

進行状態の権威はデータベースに置き、メモリ上の変数を権威としません。

#### フェーズ遷移

フェーズ遷移は、**遷移前の状態を WHERE 条件に含めた UPDATE** で行います。

```sql
-- 1. 自分の確定を立て、書いた直後の値を受け取る
UPDATE pairs SET confirmed_a = true
 WHERE id = $1
RETURNING confirmed_a, confirmed_b;

-- 2. 両者確定していたら遷移する
UPDATE pairs SET phase = 'implementation'
 WHERE id = $1 AND phase = 'prediction';
```

2 の影響行数で動作を決めます。

| 影響行数 | 動作 |
| --- | --- |
| 1 | 自分が遷移させた。二人に通知を送る |
| 0 | 既に遷移済み。何もしない |

**すべてのフェーズ遷移でこの形式を用います。**

#### データモデル

```
teachers     id, name
sessions     id, teacher_id, room_code, maze_id, status, created_at
students     id, session_id, seat_no, display_name, token, last_seen_at
pairs        id, session_id, student_a_id, student_b_id,
             round, phase, confirmed_a, confirmed_b, updated_at
programs     id, pair_id, author_id, target('self' | 'opponent'),
             round, version, cards(jsonb), created_at
simulations  id, pair_id, round, kind('ghost' | 'real'),
             requested_by, program_ids, created_at
```

- `pairs` の 1 行がフェーズ遷移の UPDATE 対象になります
- `programs.cards` には **QRカードを読んだ順の生の列**を格納します。展開後の命令列や実行軌跡は保存しません
- `programs`（予測の更新履歴）と `simulations`（試行の記録）は別テーブルとします

### シミュレーション

シミュレーションは**すべてのフェーズにおいてサーバーで実行します**。

#### 実行フェーズで走らせる世界

| # | 世界 | 構成 |
| --- | --- | --- |
| 1 | 実体世界 | A実 ＋ B実 |
| 2 | A用ゴースト世界 | A実 ＋ Aが予測したB |
| 3 | B用ゴースト世界 | B実 ＋ Bが予測したA |

#### 迷路インスタンス

「穴をうめる」によって地形が世界ごとに分岐するため、**迷路の状態は世界ごとに独立したインスタンスとして保持します**。静的な地形データを共有参照しません。

#### 軌跡のデータ形式

世界ごとに 1 本のフレーム列を生成します。

```
Frame = {
  turn: number,
  robots: { id, floor, x, y, dir, status }[],
  mazeChanges: { floor, x, y, becomes }[]
}
```

#### 振り返りフェーズの比較

「同じ動きを別の書き方で実現している箇所」の判定には、**展開後の命令列**を用います。実行軌跡は用いません。

```
展開後が一致 かつ 生の列が不一致 → 「同じ動きを別の書き方で実現している箇所」
```

### 配信の制御

実行フェーズで各児童に送るものは以下の通りです。

| 宛先 | 送るもの |
| --- | --- |
| 児童A | 実体世界の軌跡 ＋ **A用**ゴースト世界の軌跡 |
| 児童B | 実体世界の軌跡 ＋ **B用**ゴースト世界の軌跡 |

命令列（`cards`）は振り返りフェーズまで送りません。

## 実装順序

| # | 内容 |
| --- | --- |
| 1 | 骨格 — モノレポ、サーバー起動、DB 接続、WebSocket 疎通 |
| 2 | 接続の成立 — セッション作成 → ペア編成 → 参加 → トークン発行 → 切断 → 再接続 |
| 3 | シミュレーションエンジン（純粋関数） |
| 4 | プログラムのパース — 生の列 → 木 → 展開 |
| 5 | フェーズ状態機械 |
| 6 | 予測フェーズ → 実装フェーズ |
| 7 | 実行フェーズ — 3世界の実行と `view/` による配信 |
| 8 | 説明・議論・振り返りフェーズ |
| 9 | QRコードの読み取り UI |
| 10 | 描画 — 4台の重ね合わせ、ゴースト世界は半透明 |

2 までで MVP の接続要件を満たします。

## 検証

| 対象 | 方法 |
| --- | --- |
| シミュレーションエンジン | ユニットテスト（衝突スキップ、穴埋めによる地形分岐、鍵の消滅、手数超過） |
| フェーズ遷移の競合 | 2クライアントから同時に確定を投げる統合テスト |
| 離脱検知 | 片方のソケットを強制切断し、相手の画面が固まらないことを確認 |
| 再接続 | トークンを保持したままタブを閉じ、開き直して同じ状態に戻ることを確認 |
| 情報の非対称性 | 児童Aへのペイロードに B用ゴースト世界と命令列が含まれないことをテストで固定 |
