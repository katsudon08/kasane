# 実装計画（11/13まで）

## 進め方

- 1タスク＝AIへの1回の依頼＝1PRにする。依頼には「このファイルの〇〇節を実装して」と仕様書の場所を指定する
- AIが書いたコードは、各タスクの「完了の条件」と既存の確認コマンド（`mise run check`・`typecheck`・`test`・`build`。lefthookがcommitとpushで、CIがPRで実行する）で確かめてからマージする
- 純粋関数（`packages/core`、`apps/student`の編集の関数）は仕様の表をそのままテストケースにし、テストを先に書かせる
- 実機（GIGA端末）でしか分からないカメラと3Dの性能は、2日目の最初に確かめる（後で分かると作り直しになるため）

### 機械的なゲート（実装に入る前に用意する）

| ゲート             | 中身                                                                                                                                                                                                                                                                        |
| ------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 型チェック・Lint   | 既存の`tsconfig`（`strict`）とoxlint・oxfmt（`mise run check`）                                                                                                                                                                                                             |
| 依存ルール         | `apps/teacher`・`apps/student`はsteiger（FSD）。`apps/api`はoxlintの`no-restricted-imports`で、`domain`が`infrastructure`・`presentation`を読み込めないようにする。`packages/core`は依存を持たない（`package.json`の`dependencies`を空に保つ）                              |
| スキーマ検証       | backend.mdのテーブルをDrizzleのスキーマに写し、`drizzle-kit generate`でマイグレーションを作る。`drizzle-kit check`でスキーマとマイグレーションの一致をテストで確かめる                                                                                                      |
| コントラクトテスト | APIの各ルートに入力と応答のTypeBoxスキーマを書き、テストは`app.handle()`で呼んで応答が応答スキーマに合うことを`Value.Check`で確かめる。backend.mdの表（パス・入力・出力・状態コード）がそのままテストケース                                                                 |
| E2E                | Playwrightで主要な流れ（授業を始める→参加→チュートリアル1をクリア→迷路を作る→授業を終える）を実装より先に書く。カメラは偽の映像（`--use-fake-device-for-media-stream`とQRの動画）で動かす。主要画面のスクリーンショットを出力する。`mise run e2e`として足し、CIでも実行する |

### ごまかし防止

- Claude Codeのフック（`PreToolUse`）で、テスト（`**/*.test.ts`・`e2e/**`）と設計書（`docs/specs/**`）への書き込みを拒否する。テストと設計書を変えるのは人だけ
- 完了の条件は「既存の確認コマンドとE2Eがすべて通ること」。新しい確認コマンドは作らない
- `skip`したテスト・`any`・空の`catch`・`TODO`は、スクリプトではなくoxlintのルールで禁じる（ルールの追加は人が行う）

### AIレビュー層

- 実装とは別のコンテキストのサブエージェントに「仕様書（`docs/specs/single`）との差分を探せ」と依頼する。作った本人には見せない
- セキュリティは別のサブエージェントで、backend.mdの「アクセス制御」「そのほかのセキュリティ設定」をチェックリストにして見る
- レビューの基準は仕様書（`docs/specs/single`）とCLAUDE.md。設計判断の記録（ADR）は作らない

### 人のチェックを速くする

- タスクごとにレポートを書かせる。項目は「仕様書のどの節を実装したか」「仕様から外れた点」「勝手に置いた仮定」「未完了」「確かめられなかったこと」。人が読むのはこれだけ
- シードデータ（教師1人・授業1つ・児童3人・迷路2つ・挑戦の記録）と、起動コマンド1つで動作確認できる手順書を書かせる
- E2Eのスクリーンショットを先に見て、気になった画面だけ実機で触る

### 安全策とブランチ

- auto modeで回すのは開発用コンテナの中だけにし、本番の認証情報は渡さない（Neonは開発用プロジェクトの`develop`ブランチ、Railwayの本番の環境変数は渡さない）
- タスクごとにコミットし、壊れたら戻せるようにする
- `main`では作業しない。`main`から`develop`を切り、機能ごとに`develop`から`<type種別>/<英語のケバブケース>`を切って、`develop`へsquashマージする。また、planのタスクについてはAI駆動開発と自前での開発を区別するためにIssueは発行せずに開発を進める。ここでの`type`というのはconventional commitsで使用されるものを指している。`main`へは`develop`からリリース時にだけマージする。この仕様書のブランチ（`docs/20-specs-and-docs-design`）は`develop`を作った後、`develop`へsquashマージする

## 遅れたときに削る順番

1. 自分の迷路の「変える」「消す」（新規作成だけ残す）
2. プレイ画面の右上のミニマップ
3. 教師の再接続の帯（つなぎ直しだけ残す）
4. チュートリアルを7問から5問へ（No.3とNo.7を外す）

削らないもの: アクセス制御、チュートリアルを解いてクリアが記録される流れ、教師の進み具合一覧、既存の確認コマンドとフックによるごまかし防止。
