# 仕様書

## 1. 前提条件

本サービスは別リポジトリである[ProgPath](https://github.com/katsudon08/prog-path)の後継にあたります。

児童はそれぞれが自分のロボットを操作し、二人一組で迷路を攻略します。
教師は各児童ペアの状況を確認し、適切に支援を行います。

迷路にはそれぞれの児童専用のゴールが設置されていて、二人がゴールしたらクリアです。

児童がそれぞれプログラムを作成してから実際に迷路をクリアするまでのフローを以下に明示するので、この仕様書内ではこれを元にしていきます。

```md
## 個人フェーズ
前提として、このフェーズでの児童の発話は許可されていません。
児童がカンニングすることを防ぐためです。

ここで自分のロボットのプログラムと相手のロボットの動きを予測するためのプログラムを作成します。
**ゴースト世界**で自分のロボットと自分が予想した相手のロボット(ここではゴーストと呼称します)を同時に走らせて何度でも検証することが可能です。
このフェーズ内で予測が完了するまでは**何度でも**プログラムを変更することが可能です。

検証が終了して予測を確定させたらプログラムの変更をロックし、ペアの児童に予測が完了したということを通知します。(ただし、自分が作成したプログラム自体は共有されません)

ここで、双方の予測が確定すると次のフェーズへと遷移します。

↓

## 説明フェーズ
このフェーズから児童の発話が許可されます。

前提として、個人フェーズで各児童が作成したプログラム(自分のプログラムと相手の予測のプログラム)は変更不可となっています。

ここでプログラムは開示されません。
なので、児童は自分がどのように動くのかと相手の動きをどう予測したのかというのを自分の口で言語化して説明する必要があります。

↓

## 実行フェーズ
ゴースト世界と対となる**実体世界**で、**自分のプログラム**と**相手の実際のプログラム**を組み合わせて実行します。

ここで自分が元々作成していた通りの動きをするロボットを**ゴースト**、相手のロボットの動きを考慮して動くロボットを**実態**と呼称します。

画面には相手のロボットはそのまま表示され、自分のロボットについては実態とゴーストが重なって表示されます。

↓

## 確認フェーズ
差異として表示するのは児童と教師とで異なります。

児童側で表示されるのは、**何手目で最初にずれたのか**という情報です。

教師側で表示されるのは**全体のずれている手の数**です。(ここは実装時に割合での実装も検討します)

それぞれ、以下の項目ごとに表示します。

- 相手のゴーストと相手の実態 (相手のプログラムを正しく予想できているかを把握するため)
- 自分のゴーストと自分の実態

↓

## 修正フェーズ
確認フェーズで見つけたどこがずれているのかという情報を元に、改善の方針を児童間で話し合います。
ここで決めるのはあくまでも方針であって、プログラムについて話し合うわけではありません。

方針が決定したら、最初の個人フェーズへと戻りプログラムを再作成します。

また、手数の予算を超過した場合はこのラウンドは失敗扱いとなり、ゴールまで到達していても修正フェーズへと移行します。
```

## 2. 児童が組むプログラム

児童一人につき二つのプログラムを作成します。

自分のロボットをどう動かすかを決める **「自分のプログラム」** と相手がどう動くのかを予測する **「相手のプログラム」** の二種類です。

二つとも**QRカード**を使って作成します。

予測をプログラムとして組ませることで、相手のロボットがどうやって動くのかを実際に**分解・手順化**して考える必要が生じるため、入力方法を統一させています。

---

## 3. ゴーストと差分

### 3.1 生成規則

```
ゴースト世界 = simulate(自分のプログラム, 自分が予測した相手プログラム, 実行規則)
実体世界     = simulate(自分のプログラム, 相手の実際のプログラム,     実行規則)
```

予測プログラムは **干渉込み** でシミュレートする（単体走行ではない）。

### 3.2 差分は2種類

| # | 比較対象 | 測るもの | 児童にとっての意味 |
| --- | --- | --- | --- |
| **甲** | 相手のゴースト vs 相手の実体 | 他者理解の正確さ | 「相手を読み違えた」 |
| **乙** | 自分のゴースト vs 自分の実体 | 読み違えが自分に及ぼした影響 | 「その代償を払った」 |

**論理関係**: 乙 > 0 ⇒ 必ず甲 > 0（逆は成り立たない）

甲が原因、乙が結果である。甲を測らずに乙だけ測ると、
「読み違えたが干渉が起きなかったため無傷だった」ケースを見逃す。

### 3.3 比較基準

コマンド列ではなく、**1手ごとの盤面状態の系列** を比較する。

理由: `ループ(前進)×4` と `前進×4` は動きが同一である。
コマンド列で比較すると、抽象化ができている児童ほど「外れ」と判定されてしまう。
児童が理解すべきなのは相手のロボットの動きであって、記述スタイルではない。

### 3.4 提示方法

| 対象 | 見せるもの | 理由 |
| --- | --- | --- |
| 児童 | **数値なし**。「最初にずれた手数」と、その瞬間の再生 | 原因を考える手掛かりは「どこで」であって「どれくらい」ではない。数値を出すとスコアを下げるゲームになり、原因を考えなくなる |
| 教師 | 不一致手数（または不一致率）。**甲と乙を別々に** | 収束判定には単調性のある量が必要 |

最終位置の距離は採用しない。途中の経過を全て捨てるため、
「ずれ続けたが最後にたまたま同じマスに来た」場合に完璧と判定してしまう。

### 3.5 保存

**指標ではなく、盤面状態の系列そのものを生で保存する。**

指標は導出物である。系列さえ残っていれば、最終位置距離も不一致手数も
最初のずれ位置も、全て後から計算できる。
逆に指標だけを保存すると、指標を変更した瞬間に過去のデータが使えなくなる。
研究として実証データを取る以上、これは致命的である。

## 4. 相互依存の機構

| 仕掛け | 規則 | 生まれる判断 |
| --- | --- | --- |
| **ボタン** | 自分しか押せない。押すと **相手** の鍵が解放される。自分には直接の得がない | **順序**（自分の仕事と相手の仕事、どちらを先にやるか） |
| **鍵** | 相手がボタンを押した後でないと取れない。自分のゴールの解錠に必要 | **タイミング**（何手目に合わせるか） |
| **穴** | 埋めると床になる（prog-path の `穴をうめる` を流用） | **分担**（誰が埋めるか） |

### 設計思想

二人とも自分の得だけを追うと、鍵が一つも出現せず **両方失敗する**。

児童は「相手を助けなさい」と言われて助けるのではなく、
助けないと自分が損をするから助ける。そしてその因果を児童自身が失敗から導出する。

すなわちこの構造は、他者理解を道徳の問題ではなく **論理の問題** に変換している。
これが README の「教師の声掛けに依存せず、構造として成立させる」の実体である。

### 干渉の分類

- **負の干渉**（排他マスによる進路妨害）: 読み違えると損をする圧力
- **正の干渉**（ボタン・鍵・穴）: 相手がいなければ達成できない依存

負の干渉だけでは「相手 = 障害物」になり、協働的な学びにならない。
正の干渉によって初めて、相手の存在が自分の達成の前提条件になる。

### 注意点

- 「共有」は「相互作用」ではない。二人が同じ壁を見ているだけでは、
  同じ問題を別々に解いているに過ぎず、判断は増えない。
  判断が増えるのは **一方の行動によって他方の前提が変わる** 場合のみである。
- 依存を縦に入れ子にしてはならない。対称にすると循環参照で始動不能になり、
  非対称にすると先手・後手が生まれ、「一方だけが考えてもう一方が従う」状態を招く。
  現行案が優れているのは **起点が二つある** ことによる。

## 5. 実行規則

> **最上位の制約: 同じ入力なら必ず同じ出力（決定性）。ランダム要素は一切使わない。**

児童が予測できるのは、システムの挙動が予測可能な場合だけである。
実行結果が揺らげば、予測が外れた原因が児童の思考の誤りなのか
システムの揺らぎなのか区別できず、学習が成立しない。

| # | 規則 |
| --- | --- |
| 1 | **同時に1手ずつ** 進む（交互ではない） |
| 2 | 相手が今いるマスには進めない（**排他マス**） |
| 3 | 両者が同じマスを狙ったら、**両方その場に留まる** |
| 4 | ゴールに到達したロボットは **盤面から消える** |
| 5 | 待機コマンドは用意しない |

### 交互ではなく同時を採用した理由

交互制は先手と後手を必要とし、同じマスを狙ったとき先手が有利になる。
この非対称性を実行規則の最下層に埋め込むことは、
「対称性によって二人とも考えることを担保する」という本設計の原則に反する。

なお「相手がどいてからでないと入れない」という意味は、同時制でも失われない。
相手が回転コマンドを実行してその場に留まっていれば、やはり入れないためである。

### 待機コマンドを用意しない理由と、その限界

待機を封じたいが、`右, 右, 右, 右` は4手を消費して位置も向きも変えない。
`ループ(右)` を使えばカード数枚で任意長の待機が作れる。

> **コマンドを削っても、その合成で表現できるなら禁止したことにならない。**

したがって待機の封じ込めは語彙ではなく **コストの構造**（手数予算）で行う。

## 6. 手数予算

制限時間（ターン上限）を設け、**最短手数ぎりぎりまで余裕を削る**。

これにより次の二つの抜け道が同時に塞がれる。

- **待つ戦略**: 長く待てば必ず鍵が手に入る → 予算超過で失敗する
- **急ぐ戦略**: 何も考えず最速で動く → 鍵のマスに早く着きすぎ、往復で予算を失う

新たな罰則を発明する必要はない。余裕を奪えば、制限時間が罰として機能する。

### 判定基準

> **予測を組んだ児童が、組まなかった児童より確実に得をするか。**

この不等式が成り立たなければ、KASANE は「予測してもしなくても同じゲーム」になる。
児童は正直なので、必ず楽な方を選ぶ。

## 7. フェーズと沈黙

### 7.1 守るべきは「沈黙」ではなく「個人が先」という順序

敵は話し合いそのものではなく、**自分の考えを持つ前に他人の答えを受け取ること** である。
順序さえ守られていれば、話し合いは歓迎どころか必須である。

| フェーズ | 発話 | 理由 |
| --- | --- | --- |
| 自分のプログラム作成 | 禁止 | 各児童が自分の考えを形成するため |
| 相手のプログラムの予測 | 禁止 | 聞けば分かるものを予測する意味がない |
| 予測の説明・共同実行以降 | 推奨 | 個人 → 協働 の循環に必要 |

### 7.2 担保の方法: 確定（commit）

「話すな」という禁止は児童の自制に依存するため機能しない。
代わりに Git のコミットと同じ発想を採る。変更を禁止するのではなく、時点を固定する。

1. 自分のプログラムと予測を **確定** させる。確定後は変更不可
2. 双方が確定するまで次フェーズに進めない
3. 確定後は自由に話してよい（確定済みのものはもう変わらない）
4. **確定の積み重ねが、そのまま「思考の履歴」になる**

履歴機能を別途作る必要はない。確定を積み重ねれば、それが履歴である。

### 7.3 限界

確定 **前** の会話は防げない。事前に答えを合わせたペアは、
予測が当たり、差分ゼロで一発クリアする。

記録はこの抜け道を **塞がない**。可視化するだけである。
検出は教師側の観測（後述）に委ねる。

### 7.4 1回目の失敗は意図である

分担が決まっていない状態で実行させ、失敗させることで、
児童は「話さないと解けない」と自分で気づく。
話し合いを **させる** のではなく、**したくなる状態** を作る。

## 8. 教師側

### 8.1 ダッシュボードの原則

情報を消すのではなく、**フェーズごとに領域を分け、優先度で表示の重みを変える**。
沈黙フェーズのペアを大きく表示し、教師が教室の実態と見比べられるようにする。

ダッシュボードの価値は情報量ではなく **注意コストの削減** にある。
20ペアを均等に並べれば、教師は結局20ペアを見ることになり負荷は減らない。

実装上の注意:

- ペアがフェーズを移るたびに表示位置が動くと追跡不能になる。並び順の安定性が必要
- 画面上の一覧と教室内の物理的位置が結びつかないと見比べられない。座席配置に対応した並びを検討する

### 8.2 検出器: フェーズと実態の不一致

- 個人フェーズなのに話している → 抜け道
- 話し合いフェーズなのに話していない → 詰まり

システムは「今どのペアが沈黙フェーズか」を知っており、
「話しているか」は人間にしか観測できない。両方揃って初めて判定になる。

ただし教師は一人であり、指導中の数分間は他のペアを観測できない。
したがってシステム側の観測値が別途必要となる。

### 8.3 システム側の観測値

| 観測値 | 何が分かるか |
| --- | --- |
| **無操作の継続時間** | 詰まり（議論中は手が間欠的に動く） |
| **予測プログラムの作成所要時間** | 抜け道（答えを知っていれば写すだけなので速い） |
| **差分の推移**（回を追って縮むか） | **当てずっぽうの修正** |
| **差分の大きさ** | 次フェーズで詰まるかの **先行指標** |

### 8.4 差分の推移が最重要の指標である理由

README が本質的課題として挙げた次の状態を、直接検出できるのはこの指標のみである。

> ロボットが失敗するたびに理由を考えず命令を変更しても課題をクリアできるのであれば、
> 予測・原因分析・改善を伴う問題解決にはならない

理由を考えて直したなら差分は単調に縮む。
理由を考えずコマンドをいじっただけなら、差分は縮まないか暴れる。

**回数単独では判断できない。** 10回試行して差分が縮み続けるペアは、
3回で諦めたペアより優れた学習をしている。必ず差分の推移と併せて見る。

### 8.5 単一の観測値は両義的である

- 滞在時間が長い → 「深く議論している」とも「詰まっている」とも読める
- 差分ゼロ → 「読み切った」とも「事前に答えを合わせた」とも読める

必ず二つ以上の観測値を掛け合わせて判定する。
誤った判定をするダッシュボードは、教師を間違ったペアへ誘導するため、
何も表示しないより有害である。

## 9. アーキテクチャ

| 項目 | 内容 |
| --- | --- |
| 端末数 | 児童数 ＋ 教師1台 |
| オフライン動作 | **不可能**（prog-path の Electron 版の利点は失われる） |
| 通信 | WebSocket |

### 9.1 情報は2段階で流れる

1. 個人フェーズ中 → 「**確定した事実**」のみ相手に伝わる（中身は伝えない）
2. 双方確定後 → 「**中身**」が開示される

**未開示データはサーバーが保持する。**
端末に渡して表示しないだけの実装は、端末をいじれば破れる。
サーバーの役割は中継ではなく **情報の番人** である。

### 9.2 サーバーの役割

prog-path に一つも存在しないものである。

1. ルーム管理（どの端末とどの端末がペアか、どの教師のクラスか）
2. フェーズ状態機械の権威（両端末が各自で判断すると必ず食い違う）
3. 情報の出し分け
4. 確定データの保存（変更不可の担保）
5. 教師への集約配信（進捗＋操作イベント）
6. 履歴の永続化（研究データ）
7. 切断・再接続（ペアの片方だけが落ちたときの挙動を含む）

### 9.3 層分けの必須条件

> **2本のプログラムから盤面状態の系列を計算する処理を、通信・画面・保存から完全に切り離す。**

これは純粋関数である。入力（2本のプログラム＋規則）が同じなら常に同じ出力を返す。
端末が1台でも2台でも、サーバーがあってもなくても一行も変わらない。

KASANE の全機能（実行・ゴースト・差分）がここから導かれる。
通信と混ざるとテストも書けなくなる。FSD の最下層に置く。

### 9.4 開発順序

- 第一段階: 児童側（システムによる担保込み）
- 第二段階: 教師側

---

## 10. 保存する記録

- 時刻付きの操作イベント（QRカード1枚ごと）
- 確定されたプログラム（2本 × 2人）
- 盤面状態の系列（ゴースト世界・実体世界）
- 何回目のフローか

時刻は必須である。「何が」だけでなく「いつ」がなければ、
無操作時間も作成所要時間も算出できない。

| B-8 | ダッシュボードの閾値 | 無操作何分で「詰まり」とするか |

**B-1 から B-3 が埋まらないとシミュレータが書けない。最優先で決定すること。**
