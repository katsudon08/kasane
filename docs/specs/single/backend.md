# データモデル・API・アクセス制御・性能

## 全体の流れ

```
                    ┌──────────── サーバー（apps/api、1台） ───────┐
 教師 ──HTTP──────→ │  授業の作成・終了                             │
 教師 ←──SSE─────── │  全児童の状態、児童の変化、授業の終了の知らせ     │
                    │                                              │
 児童A  ──HTTP──────→ │  プログラムを受け取ってcompileし、応答で返す  │
 児童A  ←──SSE─────── │  授業の終了の知らせ                           │
 児童B   …（児童Aと同じ）│                                              │
                    └──────────────────┬───────────────────────────┘
                                       │
                                  データベース（正本）
```

- 実際に通信するクライアントは、教師のブラウザ1台と児童のタブレットN台。どれも相手はサーバーだけで、クライアント同士はつながらない
- 状態を変える操作は、教師・児童ともすべてHTTPで行う
- サーバーからの知らせだけを、SSE（Server-Sent Events）で受け取る。サーバーへ送る手段としては使わない

1. 教師が授業を作り、授業QRを表示する
2. 児童が授業に参加し、児童のトークンを受け取る
3. 教師と児童が、それぞれの受け取り口（SSE）につなぐ
4. 児童が木構造のプログラムをHTTPで送る
5. サーバーは`compile`し、送った記録をDBに保存する
6. サーバーは、コンパイルの結果をHTTPの応答で児童に返し、その児童の新しい状態をSSEで教師に送る
7. 教師が授業を終えると、サーバーは教師と全児童にSSEで終了を知らせる

コンパイルにかかる時間は、上限の200ターンでも1回あたり約0.015ms（児童40人が同時に送っても約0.6ms、Node.jsで計測）です。直列に処理しても待ちは生じないので、ワーカーやキューは使いません。

### WebSocketではなくSSEにした理由

シングルモードでは、児童同士・児童と教師が直接やり取りする場面がなく、サーバーから知らせる通信は一方向だけです。

| 観点               | 理由                                                                                                                                          |
| ------------------ | --------------------------------------------------------------------------------------------------------------------------------------------- |
| 通信の向き         | SSEは一方向で、今の用途にそのまま合う                                                                                                         |
| トークンの渡し方   | `fetch`で受け取れば`Authorization: Bearer`を付けられ、HTTPのAPIと同じ`macro`で本人を特定できる。ブラウザの`WebSocket`はヘッダーを付けられない |
| 学校のネットワーク | 普通のHTTPなので、フィルタリング用のプロキシを通りやすい                                                                                      |

接続を保ち続ける負荷や、複数台にしたときに配信を共有する仕組みが要る点は、WebSocketでもSSEでも変わりません。ペアモードで双方向のやり取りが必要になったら、WebSocketを検討します。

## データモデル（Drizzle）

```ts
teachers {
  id          uuid pk default random
  tokenHash   text unique not null          // 教師のトークンのSHA-256
  createdAt   timestamptz not null default now
}

lessons {
  id          uuid pk default random
  teacherId   uuid not null → teachers.id
  createdAt   timestamptz not null default now
  endsAt      timestamptz not null          // 授業が終わる時刻。作成時は作成から5時間後、「授業を終える」でその時刻に上書き
  index (teacherId, createdAt)
}

students {
  id          uuid pk default random
  lessonId    uuid not null → lessons.id      // 児童のトークンから授業を引くために、トークンのハッシュと同じ行に持つ
  name        text not null                 // 1〜20文字。check (char_length(name) between 1 and 20)
  tokenHash   text unique not null          // 児童のトークンのSHA-256
  skippedCount integer not null default 0   // 飛ばした問題の数。1〜skippedCount問目をクリアしたことにする（README.mdの「問題を飛ばす」）。check (skippedCount >= 0)
  createdAt   timestamptz not null default now
  index (lessonId, createdAt)
}

mazes {
  id          uuid pk default random
  studentId   uuid not null → students.id
  name        text not null                 // 1〜20文字。check (char_length(name) between 1 and 20)
  data        jsonb not null                // domain.mdのMazeをそのまま入れる（layers: Cell[][][]とstartDirection）
  createdAt   timestamptz not null default now
  updatedAt   timestamptz not null default now
  index (studentId)
}

attempts {                                   // 1回の挑戦（プログラムを1回送った記録）。追加だけで更新しない
  id          uuid pk default random
  studentId   uuid not null → students.id
  tutorialNo  integer null                  // 1から始まる番号
  mazeId      uuid null → mazes.id on delete cascade   // 迷路を消すと、その迷路への記録も消す（一覧で読む機会がなく、残しても使い道がない）
                                            // check ((tutorialNo is null) <> (mazeId is null))。ちょうど一方だけ入ることをDBが守る。アプリのコードが2列を同時に読む場面はない（クリア数はtutorialNoだけ、今の問題の結果もどちらか片方だけを見る）
  program     jsonb not null                // domain.mdのProgram（木構造）をそのまま入れる
  succeeded   boolean not null              // compileの結果がgoalだったか
  createdAt   timestamptz not null default now
  index (studentId, createdAt)
}
```

- コンパイルの結果（各ターンの位置）は保存しない。必要になれば`program`と迷路から計算し直せる
- クリア数・今の問題・今の結果は保存せず、`attempts`から求める（次の節）
- 自分の迷路は後から作りかえられるので、`succeeded`は「送った時点の迷路で成功したか」を表す。迷路を消すと、その迷路への`attempts`も消える（教師に見せる「今の問題の結果」は、残っている記録から求め直す）
- 授業が終わっているかは`endsAt <= now`で判定する（`isLessonEnded(lesson, now)`として`packages/core`の純粋関数にする）
- `endsAt`は作成時にサーバーが`lessonEndsAt(now)`（`packages/core`。作成から5時間後。午前の4コマと休み時間に、1時間の余裕を足した長さ）で計算して入れる。5時間という長さは`core`の定数で、DBには結果の時刻だけを持つ
- 教師が「授業を終える」を押したら`endsAt`を今の時刻で上書きする。教師が終えたのか時間切れなのかは区別しない（画面で使わない）
- 判定は、HTTPの要求のたび、SSEに接続するとき、SSEで定期的に空の知らせを送るときに行う。タイマーや定期処理は作らない

## 教師に見せる状態の求め方

児童ごとに、`attempts`と`students.skippedCount`から次のように求めます。教師がつないだときは全児童分を1回の集計クエリで、児童が送ったときはその児童の分だけを求めます。

| 状態           | 求め方                                                                                                                                                |
| -------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------- |
| クリア数       | `skippedCount`に、`succeeded = true`の記録にある`tutorialNo`のうち`skippedCount`より大きいものの種類の数を足した数                                    |
| 今の問題       | クリア数がチュートリアルの数より少なければ「チュートリアル（クリア数＋1）」。全部クリアしていれば、最後に送った自分の迷路（まだ送っていなければなし） |
| 今の問題の結果 | 今の問題で最後に送った記録の`succeeded`。今の問題で一度も送っていなければ「まだ送っていない」                                                         |

```ts
type StudentStatus = {
	studentId: string;
	name: string;
	clearedCount: number;
	lastResult: "notSent" | "succeeded" | "failed";
};
```

- チュートリアルを順番に解く前提なので、プログラムを受け付けるときに`isTutorialUnlocked`で解放済みかを確かめ、解放前の問題は受け付けない
- 飛ばした問題は、送った記録がなくてもクリアしたものとして数える。飛ばした後に解いた問題は、飛ばした数の続きとして数える（1〜3問目を飛ばして4問目をクリアしたら4）
- 飛ばしたことは`attempts`に入れない（`attempts`は送ったプログラムの記録だけにする）

## トークン

| 項目             | 決定                                                                                                                                                                                                                                                                                                            |
| ---------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 作り方           | 32バイトの暗号学的な乱数をbase64urlにした文字列。DBのIDや連番はトークンにしない                                                                                                                                                                                                                                 |
| 送り方           | `Authorization: Bearer {トークン}`。URLには入れない（履歴やログに残るため）。HTTPSのみ                                                                                                                                                                                                                          |
| サーバーでの保存 | SHA-256のハッシュだけを保存する（照合のため）。DBが漏れてもトークンそのものは分からない。トークンは推測できない乱数なので、パスワード用の遅いハッシュ（bcryptなど）は使わない。ソルトも付けない（候補を列挙できない乱数には事前計算の脅威がなく、行ごとのソルトは届いたトークンだけで行を探す照合と両立しない） |
| フロントでの保存 | `localStorage`（送るため）。教師のトークンと児童のトークン                                                                                                                                                                                                                                                      |
| 有効期限         | 設けない。漏れたトークンで触れるのは自分の授業だけで、授業は作成から5時間で終わるので、期限で守れるものがない。パスワードがなく本人を取り戻せないため、期限切れは別の教師になることと同じで、授業中に切れる害のほうが大きい。児童のトークンは授業の終了（`410`）が期限そのもの                                  |
| 授業のID         | `lessons.id`（`gen_random_uuid()`の乱数）をそのまま授業QRに入れる。参加コードは別に持たない。授業のIDで使えるのは授業への参加だけで、教師用APIには教師のトークンが要る                                                                                                                                          |

フロントの保存先にCookieを使わない理由: フロント（Cloudflare）とAPI（Railway）は別のサイトなので、APIのCookieは第三者Cookieになり、iPadのSafariでは既定で送られない。`sessionStorage`はタブを閉じると消え、児童が参加し直しになるので使わない。

`localStorage`はJavaScriptから読めるので、XSSを起こさないことが防御の中心になる。

- Reactの自動エスケープに任せ、`dangerouslySetInnerHTML`は使わない
- 児童画面のルビは、`<ruby>`入りのHTML文字列ではなく、Reactの部品（`<ruby>`と`<rt>`を要素として組む）で描く。名前・迷路の名前・数字のような可変部分は要素の子として差し込み、文言の文字列に連結しない
- 利用者が入力した値（児童の名前・迷路の名前）は、常にテキストノードとして描く。`program`・`data`・授業のIDは画面に文字列として出さない（TypeBoxで形・列挙値・UUIDを検証し、描画にだけ使う）
- CSPで、読み込めるスクリプトを自分のオリジンに限る（具体の指示は[そのほかのセキュリティ設定](#そのほかのセキュリティ設定)）
- 外部のスクリプトを読み込まない
- `innerHTML`・`outerHTML`・`insertAdjacentHTML`・`document.write`・`eval`・文字列を渡す`setTimeout`/`setInterval`は使わない。利用者の入力を`href`や`src`に入れない（`javascript:`のURLを作らせない）
- Trusted Types（`require-trusted-types-for`）は入れない。対応ブラウザーがそろっておらず、上の決まりでHTML文字列を扱う場所自体をなくしているため
- 参考: [MDN クロスサイトスクリプティング（XSS）](https://developer.mozilla.org/ja/docs/Web/Security/Attacks/XSS)

トークンが盗まれたときの被害は次のとおり。

- 児童のトークン: その児童の分だけで、授業が終われば使えない
- 教師のトークン: 期限はないが、見えるのは名前と進み具合だけ（個人情報は持たない）

## エラーの応答

サーバーは状態とコードだけを返し、画面に出す文言は返しません。文言は、児童画面・教師画面がそれぞれの相手に合わせて決めます。

| 状況                                                         | 状態                                        | 本文                                                                                                                                                          |
| ------------------------------------------------------------ | ------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| トークンがない・正しくない                                   | `401`（`WWW-Authenticate: Bearer`を付ける） | `{ code: "unauthorized" }`                                                                                                                                    |
| 他人の授業・迷路、存在しない                                 | `404`                                       | `{ code: "notFound" }`                                                                                                                                        |
| 授業が終わっている（SSEの接続時も含む）                      | `410`                                       | `{ code: "lessonEnded" }`                                                                                                                                     |
| 入力が正しくない                                             | `422`                                       | `{ code: "invalidInput" }`                                                                                                                                    |
| チュートリアルが終わっていないのに迷路を作る                 | `403`                                       | `{ code: "mazeLocked" }`                                                                                                                                      |
| 解放前のチュートリアルに挑戦する（`isTutorialUnlocked`が偽） | `403`                                       | `{ code: "tutorialLocked" }`。存在しないのではなく鍵がかかっているだけなので、`404`ではなく`403`。`no`が1〜チュートリアルの数の外なら`422`                    |
| 授業の児童の数が上限に達している                             | `403`                                       | `{ code: "lessonFull" }`。授業はあるが今は受け付けないだけなので、`404`ではなく`403`（`404`にすると、児童画面が「QRコードをもう一度写してね」と出してしまう） |
| 本文が16KBを超える                                           | `413`                                       | なし（サーバーが本文を読み込む前に返すので、本文もCORSのヘッダーも付かない）                                                                                  |

## HTTPのAPI

トークンの発行、授業の作成・終了、プログラムの送信、迷路の保存など、状態を変える操作と取得はすべてHTTPで行います。入力はElysiaの`t`（TypeBox）で型・長さ・範囲を検証します。

応答に入れるIDは、`id`ではなく`lessonId`・`studentId`・`mazeId`のように何のIDかが分かる名前にします（受け取った側のコードで取り違えないため）。DBの列名は`id`のままです。
行を作る操作（`POST /teachers`・`POST /lessons`・`POST /students`・`POST /me/tutorials/:no/attempts`・`POST /me/mazes/:mazeId/attempts`・`POST /me/mazes`）は`201`で返します。
トークンが要らないのは、本人の行を作る`POST /teachers`と`POST /students`の2つだけです。`POST /students`はまだ本人を特定できないので、授業は本文の`lessonId`で受け取ります（トークンが要る口は`/lessons/:lessonId`のようにパスで受け取る）。

### 教師用（`Authorization: Bearer {教師のトークン}`。`POST /teachers`以外）

| メソッド・パス                  | 入力 | 出力                                      | 備考                                                                                                                                                                                                                    |
| ------------------------------- | ---- | ----------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `POST /teachers`                | なし | `{ token }`                               | トークンがないときだけ呼ぶ。`401`を受けたらアプリは保存したトークンを消してこれを呼び直し、画面には何も出さない（教師にはトークンという概念がなく、表示しても判断できない）                                             |
| `POST /lessons`                 | なし | `{ lessonId }`                            | 既存の`POST /rooms/create`を置き換える                                                                                                                                                                                  |
| `GET /lessons`                  | なし | `{ lessonId, createdAt, studentCount }[]` | 開いている授業のみ、新しい順                                                                                                                                                                                            |
| `GET /lessons/:lessonId`        | なし | `{ createdAt }`                           | 進み具合の見出し「11月6日10:40に始めた授業」のため。他人の授業・存在しない授業は`404`、終わっていれば`410`（「この授業は終わっています」）。QR画面では使わない（QRはURLの`lessonId`と`STUDENT_ORIGIN`から画面側で作る） |
| `POST /lessons/:lessonId/close` | なし | `204`                                     | `endsAt`を今の時刻で上書きし、`204`を返す。その授業の送り先すべて（押した教師の接続も含む）に`ended`を送って閉じる。押した画面は`204`でホームへ移動し、その後に届く`ended`は無視してよい                                |

### 児童用（`Authorization: Bearer {児童のトークン}`。`POST /students`以外）

| メソッド・パス                    | 入力                 | 出力                                  | 備考                                                                                                                                                                                                                                                                                                                                                                                                                           |
| --------------------------------- | -------------------- | ------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `POST /students`                  | `{ lessonId, name }` | `201` `{ token }`                     | 児童の行を作り、トークンを発行する。授業がなければ`404`、終わっていれば`410`、その授業の`students`の行が300以上なら`403 lessonFull`（行は作らない）。作った後、その授業の教師のSSEに`student`を送る。同じ授業に同じ`name`の行があっても新しく作る（名前にユニーク制約を付けない。名前で引き継ぐと、QRと名前を知るだけで他の児童の記録を乗っ取れるため）                                                                        |
| `GET /me`                         | なし                 | `{ name, clearedCount }`              |                                                                                                                                                                                                                                                                                                                                                                                                                                |
| `POST /me/tutorials/:no/attempts` | `{ program }`        | `201` `CompileResult`                 | チュートリアル`no`（1から始まる番号。`TUTORIALS[no - 1]`）に挑戦する。`compile`して記録を保存し、教師にその児童の`StudentStatus`を送る。解放前のチュートリアルは`403 tutorialLocked`、`no`が範囲外なら`422`                                                                                                                                                                                                                    |
| `POST /me/tutorials/skip`         | `{ to }`             | `204`                                 | `to`問目から始められるよう、1〜`to - 1`問目をクリアしたことにする（`skippedCount`を「今の値」と「`to - 1`」の大きいほうにする）。`to`は2〜チュートリアルの数＋1（＋1は全部飛ばす）で、外れていれば`422`。減らすことはないので、何度送っても同じ結果になり、今のクリア数より前の問題を選んでもクリア数は減らない。保存後、教師にその児童の`StudentStatus`を送る                                                                 |
| `POST /me/mazes/:mazeId/attempts` | `{ program }`        | `201` `CompileResult`                 | 自分の迷路に挑戦する。処理は上と同じで、迷路を`mazes`から`id = :mazeId AND studentId = 本人`で読む。なければ`404`。対象をパスに置き本文を`{ program }`だけにするのは、一つの口で本文を和にすると検証の失敗が分かりにくく、処理も本文で分岐するため                                                                                                                                                                             |
| `GET /me/mazes`                   | なし                 | `{ mazeId, name, data, updatedAt }[]` | `updatedAt`が新しい順、同じなら`mazeId`順（並びを決定的にする）。`data`はホームのミニマップに使う。画面は`canCreateMaze(clearedCount)`が真になるまで呼ばない                                                                                                                                                                                                                                                                   |
| `POST /me/mazes`                  | `{ name, data }`     | `201` `{ mazeId }`                    | `canCreateMaze(clearedCount)`が偽なら`403 mazeLocked`。`data`はTypeBoxと`validateMaze`で見て、だめなら`422`。保存後、端末は`GET /me/mazes`を無効化してしょうさい画面へ。QRで取り込んだ迷路も同じ口で保存する（サーバーはどこから来た迷路かを区別しない）                                                                                                                                                                       |
| `PUT /me/mazes/:mazeId`           | `{ name, data }`     | `204`                                 | `name`と`data`を丸ごと置き換え、`updatedAt`を今の時刻にする。`id = :mazeId AND studentId = 本人`でなければ`404`。`POST`と同じく`403 mazeLocked`と`422`も見る（クリア数は減らないので起きないが、同じ検査を通す）。応答に本文がないのは、端末が送った`name`と`data`以外に伝えるものがないため（`204`は応答の本文がないという意味で、要求の本文とは関係ない）。同じ児童が2つのタブで同じ迷路を直したら、後から保存したほうが残る |
| `DELETE /me/mazes/:mazeId`        | なし                 | `204`                                 | `id = :mazeId AND studentId = 本人`の行を消す。なければ`404`。その迷路への`attempts`は外部キーの`on delete cascade`で一緒に消える。端末は`GET /me/mazes`を無効化してホームへ                                                                                                                                                                                                                                                   |

- 児童用・教師用とも、授業が終わっていれば`410`を返す（`POST /students`も含む）

## サーバーからの知らせ（SSE）

受け取り口は教師用と児童用の二つです。教師用は`GET /lessons/:lessonId/events`（`Authorization: Bearer 教師のトークン`。他人の授業なら`404`、終わっていれば`410`で、接続は始まらない）。児童用は`GET /me/events`（`Authorization: Bearer 児童のトークン`。児童はトークンから授業が引けるのでパスにIDを持たない。トークンが児童の行に当たらなければ`401`、授業が終わっていれば`410`で、接続は始まらない）。どちらも`GET`で、ここから状態を変えることはできません。

| 受け取り口                            | いつ                                       | 届くもの                                                      |
| ------------------------------------- | ------------------------------------------ | ------------------------------------------------------------- |
| 教師用（`/lessons/:lessonId/events`） | つないだ直後                               | `snapshot`: 全児童の`StudentStatus[]`                         |
| 教師用                                | 児童が参加したとき・プログラムを送ったとき | `student`: その児童の`StudentStatus`（状態全体）              |
| 児童用（`/me/events`）                | つないだ直後                               | 何も送らない（つないだ時点で終わっていれば`410`で始まらない） |
| 教師用・児童用                        | 授業が終わったとき                         | `ended`。送った後に接続を閉じる                               |
| 教師用・児童用                        | 10秒未満ごと                               | 空の知らせ（接続を切られないため。画面では使わない）          |

```ts
type ServerEvent =
	| { event: "snapshot"; data: StudentStatus[] }
	| { event: "student"; data: StudentStatus }
	| { event: "ended"; data: null };
```

- 児童の状態は差分ではなく、その児童の状態全体を送る。画面は児童のIDで上書きするだけなので、重複や順番の入れ替わりがあっても正しく表示される
- 教師がつないだときは、先に授業の送り先に登録し、その後でDBから全児童の状態を読んで送る（逆の順番だと、その間の変化を取りこぼす）
- 児童がプログラムを送ったときの順番は、`compile` → `attempts`に行を入れる → その児童の`StudentStatus`をDBから求める → 教師の送り先に`student`を送る → 児童に`201`を返す。行が入ったことを確かめてから送るので、教師に届く状態は必ずDBと一致する。送り先がない（教師が開いていない）ときは何もしない。送信に失敗しても児童への`201`は変えない（教師の画面は次の`snapshot`で追いつく）
- 児童が参加したときも同じで、`students`に行を入れた後に`student`を送る
- 児童用には他の児童の状態を送らない。受け取り口を教師用と分けることで、児童用の処理にはそのコード自体を置かない
- 授業が終わっている状態でつなごうとしたら、`410`（`{ code: "lessonEnded" }`）を返す
- 授業が終わっていないことは、教師用・児童用とも、送り先に登録した後にDBを読み直して確かめ、終わっていれば送り先から外して`410`を返す
  - 登録の前に確かめるだけだと、確かめてから登録するまでの間に授業が終わったとき、`ended`を取りこぼす（`ended`が届くのは、送る時点で登録されている送り先だけ）
  - 授業を終える側は`endsAt`を上書きしてから`ended`を送るので、読み直した結果が終わる前なら、その後の`ended`は必ず届く
  - 本人の特定（`401`）と、教師用の他人の授業・存在しない授業（`404`）は、登録の前に返す（他人の授業の送り先に登録しない）
  - 終わった授業のIDをメモリに覚える方法は採らない（DBと同じ事実を二か所に持つことになり、いつ消すかの決まりも要る）
- 空の知らせを送るたびに`isLessonEnded`を確かめ、`endsAt`を過ぎていれば終了を知らせて閉じる（押し忘れの場合もタイマーなしで知らせられる）
- 空の知らせを10秒未満ごとに送るのは、Bunが無通信の接続を既定の約10秒で切るため
- 授業ごとの送り先は、サーバーのメモリ上の`Map<lessonId, Set<送り先>>`で、教師用と児童用を別の`Set`に持つ（`student`を児童に送らないため）。同じ人が複数のタブで開けば、それぞれが送り先になる。送り先はプロセスの中にしかないので、Railwayのサーバーは1台で動かす
- 児童用の流れ: トークンのハッシュで`students`を引き（`lessons`を結合）、当たらなければ`401`、`isLessonEnded`なら`410`を返して終わる。通れば授業の児童用の`Set`に登録し、`endsAt`をDBから読み直して、終わっていれば`Set`から外して`410`を返す。終わっていなければ、以後は空の知らせと`ended`だけを送る。トークンの確認は接続の始めに一度だけで、つないだ後に`401`になることはない
- フロントはEden Treatyで`GET`し、`for await`で1件ずつ受け取る。`fetch`の`signal`で、画面を離れたら切る。Edenに再接続の機能はないので、切れたら自分で再接続する

### 再接続

- 切れたとみなすのは、サーバーが閉じた（`for await`が終わった）、通信が失敗した（`fetch`が例外を投げた）、20秒なにも届かない（空の知らせは10秒未満ごとに来るはずなので、その2倍）のどれか
- 間隔は固定3秒に0〜1秒のばらつきを足す（40台が同時につなぎ直すのを少し散らす。規模が小さいので、だんだん延ばす方式は採らない）
- 画面が見えていない間（Page Visibility APIの`document.visibilityState`が`"hidden"`）はつなぎ直さない。見えるようになった（`visibilitychange`）らすぐつなぎ直す。タブレットのスリープと、他のアプリへの切り替えがこれに当たる
- `navigator.onLine`が`false`の間はつなぎ直さず、`window`の`online`イベント（`addEventListener`で登録）を待ってすぐつなぎ直す。`true`は「ネットワークにつながっている」ことしか意味せず、サーバーに届く保証ではないので、`true`のときはふつうに試す
- つなぎ直して`401`・`410`が返ったときの扱いは初回と同じ。教師は`snapshot`が届くので`Map`を丸ごと置き換え、切れていた間の変化に追いつく
- 児童の画面には何も出さない（受け取るのは`ended`だけで、切れていてもプログラムの送信は使える。`ended`を取りこぼしても次の操作の`410`で`/ended`へ行く）
- 教師の画面は、5秒以上つながらないときだけ上部に帯を出す（回る印＋「つながっていません。つなぎ直しています」）。つながったら消す。進み具合が古いままになることを知らせるため

## アクセス制御

「IDを知っているだけで他人のデータに触れる」状態を構造的に作らないため、次を守ります。

- トークンから本人（教師または児童）を特定する処理は、Elysiaの`resolve`（または`macro`）で一か所にまとめ、各エンドポイントには本人のIDだけを渡す。SSEの受け取り口も同じ`macro`で本人を特定する
- パスのIDを使うクエリは、必ず本人のIDも`WHERE`に入れる（例: `where lessons.id = :lessonId and lessons.teacherId = :teacherId`）。取得してからアプリ側で比較する書き方はしない
- 見つからない場合も権限がない場合も`404`を返す（存在するかどうかを漏らさない）
- トークンから一つに決まるもの（児童のトークンから決まる授業など）は、パスや本文で受け取らない。受け取ると、トークンと食い違う組み合わせを確かめる処理が必要になり、その確認漏れが他人のデータに触れる原因になる
- 児童のトークンで教師用APIは使えず、教師のトークンで児童用APIは使えない（`teachers`と`students`のトークンは別テーブル）
- 授業QRに出るのは`lessons.id`で、参加コードは別に持たない。教師用APIはすべて教師のトークンが必須なので、授業のIDを知っているだけでは教師用APIは使えない

| 誰が             | できること                                                                               |
| ---------------- | ---------------------------------------------------------------------------------------- |
| 教師             | 自分が作った授業の作成・閲覧・終了、その授業の児童の進み具合の受け取り                   |
| 児童             | プログラムを送ってコンパイルの結果を受け取る、自分の迷路の作成・閲覧・編集、問題を飛ばす |
| 授業のIDを知る人 | その授業に児童として参加すること（授業が開いている間だけ）                               |

### そのほかのセキュリティ設定

- CORS: `origin`は`TEACHER_ORIGIN`と`STUDENT_ORIGIN`の二つだけ許可する
- エラーの応答にスタックトレースやSQLを含めない（既存の`errorHandler`）
- フロントエンドはCloudflareの`_headers`で`X-Content-Type-Options: nosniff`、`Referrer-Policy: strict-origin-when-cross-origin`、`Permissions-Policy`（児童は`camera=(self)`、教師は`camera=()`）を付ける
- CSPは次の指示にする。`default-src 'self'`、`script-src 'self'`（Viteのビルドはインラインのスクリプトを出さないので、nonceやhashは要らない）、`connect-src 'self' {APIのオリジン}`、`img-src 'self' blob: data:`（QRの表示とカメラ）、`font-src 'self'`（フォントは自前配信）、`object-src 'none'`、`base-uri 'self'`、`frame-ancestors 'none'`。`style-src`は`'self' 'unsafe-inline'`にする。MantineのスタイルプロパティとReact Three Fiberの`<Canvas>`が`style`属性（インラインのCSS）を使い、属性にはnonceもhashも付けられないため。`'unsafe-inline'`を許すのはスタイルだけで、スクリプトには決して許さない（CSSからスクリプトは動かせず、CSSによる外部への送信も`img-src`・`font-src`・`connect-src`を自分のオリジンに限っているので成立しない）。QR読み取りのWASMを外部から読む場合は、自前で配信するかCSPに追加する（同じく実機確認で決める）
- 児童の本名を入れないよう、ニックネームの入力欄で案内する（個人情報を持たない）

## 性能

### バックエンド

- 教師が接続したときの全児童の状態は、`attempts`を`studentId`で集計する1回のクエリで求める
- 児童が送ったときは、その児童の分だけを集計して教師に送る
- トークンの照合は`tokenHash`のユニークインデックスで1クエリ。メモリ上のキャッシュは、遅さが計測で分かるまで入れない
- 認証が必要なHTTPの応答は`Cache-Control: no-store`

### フロントエンド共通

- HTTPで取る状態はTanStack Queryで扱う
  - `GET /lessons/:lessonId`: `staleTime: Infinity`（`createdAt`は変わらない）
  - `GET /me/mazes`: `staleTime: Infinity`、`POST /me/mazes`・`PUT /me/mazes/:mazeId`が成功したら`invalidateQueries`
  - じぶんのめいろのしょうさい・プレイ・変える画面の迷路は、`GET /me/mazes`のキャッシュから`mazeId`で探す（迷路を1件読むAPIは置かない。一覧が`data`まで持ち、書き換えるのは本人だけなので、無効化する口を一覧の一つに絞れる）。キャッシュがなければ一覧を取ってから探し、見つからなければホームへ移動する
  - `GET /me`: `staleTime: Infinity`、`POST /me/tutorials/:no/attempts`・`POST /me/tutorials/skip`が成功したら`invalidateQueries`（クリア数が変わるのはそのときだけ。自分の迷路への挑戦ではクリア数は変わらない）
- SSEで受け取る教師の進み具合は、児童のIDをキーにした`Map`で持ち、届いた児童の分だけを差し替える
- チュートリアルは`packages/core`の定数なので通信しない
- 再レンダリングを抑える
  - React Compilerを導入して自動でメモ化する（Vite 8＋`@vitejs/plugin-react`で導入できるかを最初に確かめ、できなければ`memo`/`useMemo`/`useCallback`を手で書く）
  - 進み具合の児童カードは児童のIDをkeyにし、状態が変わっていない児童は再描画しない
  - カードの並びはプレイ画面の`useReducer`で持ち、カメラのコンポーネントは並びの変化で再描画しない
- 静的ファイルはファイル名にハッシュが付くので、Cloudflareで長期キャッシュする

### 3D（React Three Fiber）

- 同時に描く`<Canvas>`は一つだけ。一覧はCSSのミニマップで描く
- `frameloop="demand"`にし、ロボットが動いている間と指で回している間だけ再描画する
- マスは種類ごとに`InstancedMesh`一つで描く（床・壁など、同じ形が多いもの）。ジオメトリとマテリアルはモジュールの定数にして使い回す
- ロボットの動きは、コンパイルの結果の`steps`を`useFrame`の中で補間し、refを書き換える（1フレームごとにReactのstateを更新しない）
- `dpr={[1, 1.5]}`で描画解像度の上限を決め、影は使わない

### カメラ

- QRの読み取り間隔は300ms程度にする
- 画面を離れたらカメラを止める（コンポーネントのアンマウントで止まることを確かめる）
